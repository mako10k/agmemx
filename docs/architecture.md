# アーキテクチャ

要件は [requirements.md](requirements.md)。この文書は、その記憶をどこに置き、どのディレクトリを文脈として解決し、開発中の文書・ソース・テストの由来をどう残すかを定める。

実行時の記憶と、開発由来の記録は別物である。信念・観測・Reference は XDG 上のドメイン木に置く。文書・ソース・テストの依存は、作業ツリーの sealgraph に置く。記憶の中身を sealgraph に書かず、sealgraph のオブジェクトを記憶の検索結果に混ぜない。

## 実行時の構成

呼び出し側は厳密なスキーマで登録・検索・更新・拒否を行う。解決ディレクトリの決定、検証、拒否はメモリ側で終える。

```text
呼び出し
  │  スキーマ、--dir または実行時ディレクトリ
  ▼
ドメイン解決 ── 正規化絶対パスの木
  │
  ▼
スキーマ検査
  │
  ├─ 信念 ──理由──▶ 信念 | 観測 | 自然文 | なし
  ├─ 観測 ──Reference──▶ 発話または文書のスパンと、そこから解決する周辺テキスト
  ├─ 順序（同一ドメイン内の次発話など）
  └─ 期間
```

矛盾しているという内容は、対象へリンクした信念としてこの同じ構造に乗る。専用の解消器は置かない。

応答のフィールド構成は仮決めのままである。返却は構造化されたスライスとし、解決範囲の全件をメインコンテキストへ展開しない。

## 記録の場所

記憶本体は次のディレクトリに置く。

```text
${XDG_DATA_HOME:-$HOME/.local/share}/agmemx/
```

`XDG_DATA_HOME` が未設定または空のときは `$HOME/.local/share` を使う。値が相対パスのときは拒否する。ワークツリーは文書とソースの場所であり、記憶本体の場所ではない。

配置は次で足りる。

```text
agmemx/
  objects/     信念、観測、Reference、順序、期間
  domains/     正規化絶対パスから、そのドメインに属する object への索引
```

オブジェクトは識別子で引く。ドメインを付け替えても本文と Reference は複製しない。索引だけを更新する。

埋め込み索引は再生成できるものとして `${XDG_CACHE_HOME:-$HOME/.cache}/agmemx/` に置く。ロックや実行中の状態は `${XDG_STATE_HOME:-$HOME/.local/state}/agmemx/` に置く。いずれも未設定または空なら規定の既定値を使い、相対パスは拒否する。

## 意味検索

自然文の検索は、解決ディレクトリの部分木を構造で絞ったあと、埋め込みで順位づけて上限までのスライスを返す。埋め込む本文は、信念または観測として保存したテキストである。Reference が指す源ファイル全体は埋め込みの入力にしない。

プロバイダは実行時に一つだけ選ぶ。初期の実装は次である。

| プロバイダ | 接続 | リクエスト形 | 鍵 |
| --- | --- | --- | --- |
| `ollama` | 既定の base URL は `http://127.0.0.1:11434`。呼び出し側が上書きできる | Ollama の `/api/embed` | なし |
| `openai` | 既定の base URL は `https://api.openai.com/v1`。呼び出し側が上書きできる | OpenAI の `POST /v1/embeddings` | `OPENAI_API_KEY` |

追加のホストは、新しいプロバイダ名を増やさず、OpenAI 互換の base URL と鍵の環境変数を明示して選ぶ。xAI の推論 API は `https://api.x.ai/v1` で、鍵は `XAI_API_KEY` である。使うモデルがその base URL で埋め込みを返すかは、呼び出し側がモデル名を指定するときに確認する。

モデル名は必須である。キャッシュの鍵は、プロバイダ、base URL、モデル名、本文のハッシュである。次元の違うベクトルは比較しない。プロバイダまたはモデルを変えたあとは、明示的な再索引でその組のキャッシュを作り直す。

登録は、プロバイダがベクトルを返したあとにオブジェクトを確定する。接続失敗、未設定、次元不一致は安定した拒否とし、オブジェクトを残さない。検索時にキャッシュが欠ける記録があるときも、黙って落とさず拒否する。

受入セッションの結合は、決定的なフィクスチャプロバイダで行う。`ollama` と `openai` のリクエスト形は、記録した応答を使う契約テストで固定する。実サーバへの到達は完了条件にしない。鍵と base URL は記憶本体にも文書にも書かない。

## 階層ドメイン

ドメインのノードはディレクトリである。識別子は、シンボリックリンクを解決した絶対パスで、末尾のスラッシュを除いたもの（ファイルシステムのルートのみ `/`）である。親ドメインは、そのパスの親ディレクトリである。

解決ディレクトリは次の順で一つに決める。

1. `--dir` があるときはそのパス。相対パスは、プロセス起動時のカレントディレクトリから解決する。
2. `--dir` がないときは、プロセス起動時のカレントディレクトリ。

その後に正規化する。正規化の結果が存在するディレクトリでないときは拒否する。ファイルシステムのルートは解決ディレクトリにしない。起動後の作業ディレクトリ変更では、解決済みのドメインを動かさない。

`--dir` が変えるのは記憶の解決ディレクトリだけである。sealgraph のストア位置や、プロセスのカレントディレクトリそのものは変えない。

規則は次のとおり。

- 登録時のドメインは、解決ディレクトリのノードである。スキーマで任意のドメイン名を新設しない。
- 既定の検索範囲は、解決ディレクトリを根とする部分木である。そのディレクトリと、子孫ディレクトリのドメインを含む。
- 祖先ドメインと兄弟ドメインは、既定の検索範囲に入らない。
- 同じ文字列でも、ドメインが違えば別のメンバーシップである。
- 会話ドメインの後付けは、所属の索引を追加または変更する操作である。観測本文の複製でも、ディレクトリの移動でもない。
- 順序関係の「同じ文脈」は同じドメインを指す。Reference が解決する周辺テキストとは別の語として扱う。

## 開発由来の sealgraph 規則

作業ツリー直下の `.sealgraph` を、このリポジトリの由来のストアとする。初期化形式は sealgraph の新規リポジトリ既定（format 5）に従う。別の作業ツリーのストアを、同じ履歴と呼ばない。

Cause の向きは、依存する側が依拠する側を指す。影響範囲は、この向きを下流へ辿って得る。逆向きのリンクや循環は作らない。root は由来の境界であり、内容が真であることは意味しない。

### REF と由来

| REF | 束縛するパス | Cause message | Cause の向き |
| --- | --- | --- | --- |
| `doc/requirements` | `docs/requirements.md` | なし（root） | 由来の境界 |
| `doc/architecture` | `docs/architecture.md` | `details` | `doc/requirements` |
| `src/<リポジトリ相対パス>` | そのソースファイル | `implements` | 実装の根拠にした `doc/...` |
| `test/<リポジトリ相対パス>` | そのテストファイル | `verifies` | 検証する `src/...`。対応するソースがまだ無い検証は `doc/...` |

メッセージは Cause message のただ一つのトークンとする。追加の意味が message では足りなくなってから、format 6 の link metadata を検討する。それまで形式移行はしない。

ソースとテストの REF 接頭辞は `src/` と `test/` を仮に使う。実ディレクトリが別になったときは、接頭辞をそのときに合わせ、既存 REF の付け替えは `mv` と revision assertion を明示して行う。空ディレクトリは登録しない。

各ソースは、実装の根拠にした文書 REF を少なくとも一つ Cause に持つ。各テストは、検証するソースまたは文書を少なくとも一つ Cause に持つ。文書からソースへ向かう Cause は作らない。ソースからテストへ向かう Cause も作らない。

初回登録は `--bind-source` で作業ツリー相対パスを束縛する。束縛はマシンローカルであり、別チェックアウトでは明示的に束縛し直す。オブジェクトを作り直して旧履歴に代えない。

### 更新と影響範囲

seal 済みの文書、ソース、テストを変える前に、対象 REF の現在の Seal に対して影響範囲を見る。

```sh
sealgraph status
sealgraph source compare REF
sealgraph impact --all-paths REF
```

`impact` の結果は、変更前の下流候補である。将来の stale 一覧そのものではない。

変更後は、その REF だけを候補へ反映して seal する。下流は `sealgraph stale --frontier` を入口に、確認した REF を一つずつ見直し、新しい Cause と `--previous` を明示して seal する。一括の relink や reseal はしない。未確認の stale は残す。

文書を更新したときの影響範囲は、その文書を Cause に持つソースと、そのソースを Cause に持つテスト、さらに文書を直接 Cause に持つテストである。要件の更新は `doc/architecture` を経由して、その先のソースとテストへ届く。

登録漏れは `impact` からも `stale` からも見えない。新しい文書・ソース・テストを追加した作業は、対応する REF の seal を終えて完了とする。

### 記録しないもの

sealgraph に登録するのは、維持する文書、ソース、テストである。次は登録しない。

- 信念、観測、Reference などの実行時記憶
- XDG 上の data、state、cache
- 秘密、環境ファイル、生成物
- `.sealgraph` の index、cache、logs、locks、tmp

Git でこのストアを残すときは、config、objects、refs を対象にする。index、cache、logs、locks、tmp はローカル専用とする。
