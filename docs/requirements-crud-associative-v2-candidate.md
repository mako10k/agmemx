# agmemx CRUD・CLI・連想検索 要件候補 v2

状態: Candidate（2026-09-28）。`v2` はこの要件候補の文書版であり、製品版・公開 API 版・CLI 契約版ではない。所有者が v1 の独立レビュー後に `REVISE` を選んだため、v1 を変更せず新しい候補とした。所有者による承認前であり、現行の [requirements.md](requirements.md)・設計・実装・PERT を置き換えない。

## 目的と由来

AI エージェントおよび人が、保存した記憶を登録後にも見つけ、内容を確かめ、修正し、不要なものを除き、関連する前後の文脈とともに取り出せるようにする。現行の信念・観測、理由、Reference、`next`、ドメイン、埋め込み検索の意味は、以下で明示する変更を除き [requirements.md](requirements.md) の制約を引き継ぐ。

今回の所有者指示は、Read に一覧・検索を含めた CRUD の完備、対称で一貫した CLI、既存 CLI・保存データとの互換を要求しないこと、Git や Docker と同じコマンド名なら意味を十分に揃えること、検索精度だけでなく近接リンクから人が連想できる手掛かりを返すこと、A→B→C の B の前後を辿れること、プリミティブな入力を原則 `--option=value` 等で渡し JSON 入力を任意経路にすることである。ドメインは canonical path に対応し、ドメイン自体の CRUD は不要だがディレクトリ移動に対応する、という所有者の追加決定も含む。以下の具体化は承認待ちの提案である。

## 提案する対象と操作

| 対象 | Create | Read | Update | Delete |
| --- | --- | --- | --- | --- |
| 信念 | 本文と任意のタイトルを登録 | ID 指定取得・ドメイン部分木の一覧・自然文検索 | 本文、タイトル、理由、対象、期間、所属ドメインを変更 | ID 指定削除 |
| 観測 | 本文・Reference と任意のタイトルを登録 | ID 指定取得・ドメイン部分木の一覧・自然文検索 | 本文、タイトル、Reference、期間、所属ドメインを変更 | ID 指定削除 |
| `next` 関係 | 同一ドメインの両端を結ぶ | 関係の識別子による取得・ドメイン内の一覧・端点からの参照 | 両端を変更 | 関係の識別子による削除 |

「完備」は、上記の各操作が公開 CLI で実行でき、成功結果を機械向け JSON で読み戻せることを指す。ID 指定取得・一覧・削除・関係操作・所属変更は埋め込みプロバイダを要求しない。信念・観測の作成と本文更新、自然文検索、明示的な再索引は埋め込みを使う。全操作は、指定したドメインの可視範囲と既存の種別・理由・Reference・同一ドメイン `next` 制約を守る。

更新後も信念・観測の ID は維持し、内容ダイジェストと埋め込みキャッシュは変更内容に合わせる、という案とする。理由・`about`・`next` から参照される記録の削除は、暗黙の連鎖削除や参照切断をせず拒否する。`next` の端点が別ドメインに移る更新も、関係を明示的に処理しない限り拒否する。拒否後は対象記録・参照・関係・所属索引・キャッシュが呼出し前と同じであり、作成・更新の埋め込み失敗でも部分更新を残さない。関係を明示的に削除し、他の参照も解消してから記録を削除できる。削除済み ID の取得・再削除は、存在しない対象として拒否する。

ドメインはファイルシステムのディレクトリを正規化した canonical path に対応する文脈・可視範囲であり、それ自体を CRUD 対象にしない。記録の所属付け替えと部分木での可視範囲解決を提供する。ディレクトリ移動後も、旧ドメインの記憶を新しい canonical path から利用でき、移動対象の識別子・本文・理由・`about`・`next` の整合を保てることを要求する。移動を明示操作で通知するか自動検出するか、子孫ドメインをどう扱うかは所有者決定を待つ。埋め込み設定・再索引は運用操作であり、記憶レコードの CRUD とは区別する。

## CLI 入出力

公開コマンドは対象ごとに同じ操作語と引数順を用い、対応する操作の有無が `help`・`schema`・補完・man と一致する。共通操作の成功形には対象の識別子・種別・所属ドメインを置き、拒否は対象固有の制約を含めて安定した意味を持たせる。対象ごとの差を説明せずに同名操作の意味を変えない。Git・Docker と同じ名前を使う場合は利用者が期待する主な意味と揃え、揃わない名前は採用しない。具体的なコマンド綴りと JSON フィールドは設計・CLI 契約で定める。

本文、タイトル、ID、期間の両端、Reference の源と範囲、理由の種別と ID、関係の種別と両端、ドメイン、検索語・件数など、プリミティブ値で表せる入力はコマンド引数・`--option=value` 形式で指定できる。複数値や入れ子の指定が必要な場合も、意味を曖昧にせず表せる範囲では反復オプションや分割オプションを提供する。JSON オブジェクト入力も選べるが、プリミティブ値だけの通常操作の必須条件にはしない。同一呼び出しで引数入力と JSON 入力を混在させる場合の優先・拒否規則は一つに定め、曖昧な部分実行をしない。

人向け text と機械向け JSON の双方で、取得・一覧・検索の対象識別子と内容を確認できる。text 表示は構造上の関係を見失わないようにし、JSON は厳密なスキーマと安定した拒否を維持する。互換エイリアス、旧コマンド・旧応答形、旧保存形式の読取・変換・保全は要求しない。新形式への破壊的な切替を許容する。旧データを切替時に自動削除するか、明示操作で削除するか、未使用のまま残すかは別の作用として所有者決定を待つ。

## 連想検索

自然文検索は、まず現行のドメイン部分木と埋め込みによる一致候補を選ぶ。類似度は入口の選択に使い、出力の価値を一致順位だけで測らない。各一致候補には、`next` の直接前後に加え、信念の理由と `about` の直接リンクでつながる可視範囲内の記録を、検索語との類似度に関係なく想起の手掛かりとして添える。例えば A→B→C が保存され、B が一致候補なら、B を中心に A と C が前後どちらか分かる。理由・`about` の手掛かりにはリンク種別と方向を付け、時系列の前後と混同させない。

一致候補と手掛かりの各記録には、識別子・種別・ドメイン・短い表示用の手掛かりを含める。タイトルは任意入力で最大 80 Unicode スカラーとする案である。利用者が登録していればそれを使い、無ければ保存本文の先頭から最大 80 Unicode スカラーを抜粋する。保存されていない要約や関係の意味を事実として作らない。候補本体と手掛かりは区別し、手掛かりを一致順位・一致件数に混ぜない。結果に含まれる ID を使って本文の取得や関係一覧へ進める。

検索の件数上限は一致候補に適用し、手掛かりは一致候補 1 件につき最大 8 記録とする案である。直接の `next` 前後がそれぞれ存在するときは各 1 件を優先し、残りは直接の `next`・理由・`about` の順と関係方向・識別子の順で決定的に選ぶ。したがって A→B→C の B が一致したときは A と C の両方を表示できる。上限超過時は省略件数を示し、全関係は ID 指定の関係一覧から辿れる。無制限に関係グラフを展開せず、同一記録が複数経路に現れた場合も識別子で照合できる。

Reference は源と範囲を維持する。観測に対する検索表示では、参照先のスパン開始位置を中心に、スパン内最大 80、前後各最大 40 Unicode スカラー、合計最大 160 Unicode スカラーの抜粋を文脈として添える案である。長いスパンを切り詰めた場合はその旨を示す。参照先が移動または消失して解決できないときは、保存済み記録を検索結果から消さず、抜粋が利用できないことを明示する。検索は Reference の文脈抜粋を返す操作であり、源ファイル全体の取得操作は設けない。

## 受入の最低例

1. 一時 XDG 領域で信念・観測・`next` を引数だけで作成し、各対象を ID 指定取得と一覧で読み戻せる。等価な JSON 入力経路も確認できる。
2. 各対象の更新を取得で確認し、記録 ID と無関係な関係・索引が意図せず変わらない。既存制約に反する更新と失敗する埋め込みは、記録・参照・関係・索引・キャッシュのどれにも部分更新を残さない。
3. 理由・`about`・`next` から参照中の記録の削除は拒否され、参照を明示的に解消した後で削除できる。削除後の取得・一覧・検索には現れない。
4. A→B→C を登録し、B にだけ類似する語で検索したとき、B を一致候補として、A と C のタイトルまたは本文抜粋を前後の文脈として区別して返す。さらに B の理由・`about` で直接つながる別記録の手掛かりを、関係種別とともに返す。手掛かりの低い類似度は除外理由にならず、件数上限は一致候補にのみ効く。上限超過時も前後各 1 件と省略件数を確認できる。
5. 全公開操作の help・schema・text・JSON・補完・man が同じコマンド体系を示し、プリミティブ操作には JSON 入力を要求しない。
6. ディレクトリの canonical path が移動しても、対応付け後の新 path から同じ ID・本文・参照関係・`next` を取得・一覧・検索できる。旧 path と無関係のドメインは変わらない。

## 所有者に残す決定

1. 関係に安定した ID を割り当て、端点の更新後も ID を維持する案でよいか。現行の `next` は `kind`・`from`・`to` の組で重複を判定し、関係 ID を持たない。組を識別子とする案では、端点変更を原子的な置換として定義する必要がある。
2. 信念・観測の更新で ID を維持し、理由・`about`・`next` から参照中の削除を拒否する案でよいか。新 ID で置換する案は履歴を明示できる一方、既存参照の扱いを別途決める必要がある。連鎖削除案は操作数を減らせる一方、意図しない消去範囲が広がる。
3. 任意の最大 80 文字のタイトル、本文先頭 80 文字の代替手掛かり、直接リンク最大 8 件の選択規則、Reference の最大 160 文字の抜粋を採用するか。さらに遠いリンクまで自動展開する案は一度に多く読める一方、出力量が増える。
4. ディレクトリ移動を明示操作で通知するか自動検出するか、移動対象に子孫を含めるか。旧データの破壊的切替時に自動削除を行うかも、同じく作用範囲として決める。これらは所有者へ別途確認中である。
