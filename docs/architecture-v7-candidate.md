# agmemx v7 基本設計候補：疎結合モジュール

状態: Candidate（2026-09-29 改訂）。この文書は基本設計のレビュー対象であり、現行の [architecture.md](architecture.md) をまだ置き換えない。

## 目的と根拠

[受入済み v7 要件](requirements-crud-associative-v7-candidate.md) とその [受入記録](requirements-crud-associative-v7-acceptance.md) に従い、記録と関係の CRUD、訂正と履歴上の変化、プロバイダ不要の書込み、非同期埋め込み、全文検索へのフォールバック、連想手掛かり、引数または JSON を選べる CLI を実現する。既存 [requirements.md](requirements.md) は v7 が明示的に変えない制約に限って引き継ぐ。設計や現行実装を使って、受入要件を狭めない。

この基本設計は**責務を分離したモジュール**を定義する。所有者は、CLI 側と埋め込み worker を別プロセスにし、Go module も複数に分ける方針を選んだ。目的は、責務を無視して他の実装を直接修正する経路を狭めることである。モジュールの接続は利用側が所有する小さな契約を介し、永続化形式、検索方式、埋め込みプロバイダ、表示形式を相互に直接参照しない。Go module の具体的なパスと構成、プロセス間の接続方式は未決定である。

## 責務と境界

| モジュール | 単独の責務 | 入力・提供する契約 | 持たない責務 |
| --- | --- | --- | --- |
| 記憶モデル | 信念・観測・Reference・理由・期間・型付き関係と、訂正／変化／削除の意味上の不変条件を定義する | 記録・関係の値と、それらが満たす意味上の制約 | ファイル、プロバイダ、CLI 引数、表示 |
| ドメイン | 起動時ディレクトリと `--dir` の canonical path 解決、部分木判定、移動前後の path 対応付けを定義する | 正規化 path、部分木範囲、移動対応要求 | 記録本体、検索順位、物理索引 |
| Reference 解決 | 源と範囲から利用可能な文脈または解決不能状態を返す | Reference と解決範囲から文脈・状態へ | 記録の削除、源ファイルの変更、検索順位 |
| 本文保管 | ハッシュを鍵として記録本文を保存・取得する | 本文ハッシュから本文へ | ID、関係、所属、CLI 構文 |
| 状態台帳 | 安定 ID と現本文ハッシュ、メタデータ、所属、関係、論理削除状態、非同期処理待ちを一つの確定単位として保存・取得する | `ReadSnapshot` と `CommitChange` に相当する読み取り・原子的変更契約 | 本文の意味、埋め込み計算、検索順位、要約 |
| 埋め込み処理 | 確定済み本文ハッシュから非同期でベクトルを作り、プロバイダ・接続先・モデル別に再生成可能な成果を管理する | 処理待ちの取得、本文ハッシュと埋め込み環境に紐づくベクトルの照会 | 記録の確定可否、記録 ID の割当、通常検索の方式選択 |
| 候補検索 | 指定部分木の生存記録から、通常検索時に埋め込み又は全文を選び、一致候補と方式を返す | `Search(scope, query, mode)` に相当する候補 ID・スコア・方式 | 関係の表示、CLI 出力、記録の更新 |
| 連想表示 | 一致候補から入出方向の関係を辿り、参照・接続統計、短い要約、重みと出力予算に従う結果を組み立てる | 候補 ID、状態台帳の読取像、予算から構造化結果へ | 一致候補の再選定、保存、埋め込み生成 |
| 記録変更 | 記録の作成・同 ID 訂正・別 ID の変化／終了・訂正削除を個別の操作として実行する。訂正削除では、同じ読取像から入出両方向の関係と内部参照リンクの削除対象を求める | 意図を明示した記録変更要求と、カスケード対象を含む変更結果 | JSON パース、フラグ、保存形式、検索順位 |
| 関係変更 | 単独の関係作成・訂正・論理削除を、記憶モデルの関係制約に従って実行する | 関係 ID・端点・種類・理由を持つ変更要求と結果 | 記録本文、記録削除のカスケード対象決定、CLI 構文、検索表示 |
| 所属変更 | 記録の所属付け替えと、ディレクトリ移動時の部分木 path 対応付けを実行する | ドメインが計算した対応付けと原子的変更要求 | 本文の複製、関係の意味、検索順位 |
| 読取操作 | 記録の ID 取得・部分木一覧・検索と、関係の ID 取得・一覧・端点からの参照を担う。記録検索は同じ読取像から候補検索と連想表示につなぐ | 記録・関係の ID、範囲、端点または検索語から構造化結果へ | JSON パース、フラグ、状態変更、HTTP プロバイダ |
| CLI 入出力 | 同じ公開操作について引数経路又は JSON 経路を選び、text 又は JSON を出力し、help・schema・補完・man を同じ操作目録に揃える | 操作要求への変換と結果の表示 | 記憶の意味、原子的確定、検索方式の独自判断 |

記憶モデルは、観測には発話・文書スパンを示す直接の `Reference` を必須とし、信念の理由は省略可能で信念・観測・自然文に限る。観測の理由に信念は使えない。矛盾は専用の状態や辺にせず、対象へリンクした「矛盾している」という信念で表す。この継承制約を記録変更で検証する。

`Reference` は外部の発話・文書スパンを示し、記憶ノード間の関係とは別に扱う。理由や `about` が記憶ノードを指す場合は、削除時の参照整合を保てるよう内部で型付きの参照として数える。外部に公開する関係の種類・識別方法は CLI 契約で定める。

## 依存方向

```text
CLI 入出力 ──▶ 記録変更／関係変更／所属変更 ──▶ 記憶モデル・ドメイン
      │                         └──────────────▶ 状態台帳の変更契約
      └──────▶ 読取操作 ──▶ 状態台帳の読取契約
                         ├──▶ 候補検索の契約 ──▶ 全文／ベクトル検索実装
                         └──▶ 連想表示の契約 ──▶ 関係読取・Reference 解決

本文保管 ──▶ 本文ハッシュから本文へ
状態台帳 ──▶ 現本文ハッシュと本文保管への参照

埋め込み処理 ──▶ 確定済み待ち行列と本文ハッシュ
候補検索 ──▶ 状態台帳の読取像、本文保管、利用可能なベクトル
連想表示 ──▶ 状態台帳の読取像、候補検索の結果
```

記録変更・関係変更・所属変更・読取操作・候補検索・連想表示は、永続化実装や HTTP クライアントを直接 import しない。CLI は各モジュールを組み立てるが、要求の意味検証を再実装しない。モジュール間では、記録 ID、本文ハッシュ、関係 ID、canonical path、検索方式、削除状態を明示的な型で渡す。埋め込み処理と候補検索の間では、プロバイダ・接続先・モデル・本文ハッシュを合わせて保存済みベクトルを識別する。埋め込み処理から状態台帳の記録を上書きする経路は設けない。

### Go module の境界

**所有者の決定:** 単一の `go.mod` 内の package 分離には留めず、複数の Go module に分ける。責務を無視した安易な横断修正を難しくすることが目的である。

**この基本設計の提案:** 上の責務表の各行を、それぞれ独立した Go module の境界とする。すなわち記憶モデル、ドメイン、Reference 解決、本文保管、状態台帳、埋め込み処理、候補検索、連想表示、記録変更、関係変更、所属変更、読取操作、CLI 入出力を別々に扱う。CLI と worker の実行入口はそれぞれの責務の module 内に置き、依存の組立てを担当する。共通の値や契約を理由に業務処理を一つの共有 module へ集めない。具体的な module path、公開 package とローカル開発時の接続方法は詳細設計で決める。この一対一の分割は所有者の「複数 module」決定から自動的に導かれるものではなく、基本設計候補としてレビューする。

**設計上の依存規則:** 記憶モデルなどの下位の値・不変条件から、CLI・worker・保存実装・検索実装へ依存しない。変更・読取のユースケースは、利用側が必要とする契約を通して下位機能を呼び、他 module の実装 package を直接 import しない。CLI と worker はそれぞれ自分の実行入口で依存を組み立てる。責務をまたぐ修正が必要なら、変更対象の契約と影響を明示し、各 module の単独検証と接続検証で確認する。Go module 分割だけでソース変更を禁止できるわけではないため、依存方向と公開 API の検証も設計に含める。

### 独立実装に必要な最低契約

以下は実装言語の関数名ではなく、モジュール間で交換する情報と結果の契約である。ポートは利用側の必要から定義し、実装側の保存形式や HTTP 応答を漏らさない。

| 利用側 → 提供側 | 渡す情報 | 返す情報・失敗時の境界 |
| --- | --- | --- |
| 記録変更 → 本文保管 | 本文バイト | 本文ハッシュ。重複本文の保存は同じハッシュに収束する。失敗時、記録 ID の状態は変えない |
| 記録変更・関係変更・所属変更 → 状態台帳 | 操作意図、対象 ID、現本文ハッシュ、メタデータ、関係の端点・種類・理由、所属 path の変更。記録の訂正削除では、入出両方向の関係と内部参照リンクを列挙した削除対象一式 | 確定後の ID・関係・所属。記録の訂正削除では、確定時点の対象に漏れがあれば変更全体を拒否する。整合違反や書込み失敗では、ID 対応、参照、関係、所属、削除状態、処理待ちを部分確定しない |
| 読取操作・候補検索・連想表示 → 状態台帳 | 記録・関係の ID、部分木範囲または関係の端点 | 同一確定時点の記録・関係・所属・削除状態の読取像。通常の取得・一覧・検索と端点からの参照では論理削除済みを除く |
| 埋め込み処理 → 処理待ち・本文保管 | 確定済み本文ハッシュと選択したプロバイダ・接続先・モデル | その組と本文ハッシュに紐づくベクトル又は未作成・失敗状態。記録の確定や現本文ハッシュは変えない |
| 候補検索 → 埋め込み照会・全文照会 | 読取像、範囲、検索語、通常又は明示埋め込みの方式指定、選択したプロバイダ・接続先・モデル | 一致候補 ID・スコア・使用方式。異なる埋め込み環境のベクトルは混ぜず、通常検索の埋め込み不能時は対象全体を全文方式にし、明示埋め込み不能時はエラーにする |
| 連想表示 → Reference 解決 | Reference の源・範囲と解決範囲 | 元の源・範囲を保持した解決済み文脈又は解決不能状態。解決不能でも記録や関係は変更しない |
| 読取操作 → 連想表示 | 同じ読取像、一致候補、出力予算 | Reference の解決状態を含み、候補と手掛かりを分けた予算内の構造化結果。候補の一致件数・順位は変更しない |
| CLI 入出力 → 変更・読取操作 | 引数又は JSON から得た型付き要求と明示した操作意図 | 型付き結果又は拒否。text・JSON 表示、help・schema・補完・man はこの公開操作目録に従う |

`状態台帳` は唯一の原子的確定境界であり、他モジュールの業務判断を集める場所ではない。各変更ユースケースは自分の操作意図を検証し、記憶モデルの意味上の制約を使って変更要求を組み立てる。記録の訂正削除では記録変更がカスケード対象を決め、状態台帳が確定時点の全対象を一括適用できることを確認する。対象に漏れがあれば全体を拒否し、部分削除を残さない。具体的な競合処理は詳細設計で定める。本文保管やベクトルキャッシュに未参照の実体が残っても、読取像に現れない限り記録の部分確定とは扱わない。具体的な型、エラーコード、同時実行制御と物理配置は詳細設計で定める。

## 保存と更新の確定境界

1. 本文は内容から決まるハッシュで参照する。安定した記録 ID から現在の本文ハッシュとメタデータへ到達できる。本文の同一性と記録の同一性を混同しない。ハッシュ対象の byte 定義は詳細設計で固定する。
2. 状態台帳の一回の変更で、ID と現本文ハッシュ、所属、Reference、関係、削除状態、必要な埋め込み処理待ちを整合させる。失敗した変更を読み手に部分適用として見せない。本文保管への新しい書込みが先行しても、確定前の本文は記録として見せない。ストレージ実装はこの原子的契約を満たす方式を選ぶ。
3. 誤記の訂正は同じ ID の新しい本文ハッシュまたはメタデータを確定し、本文が変わればそのハッシュの埋め込みを処理待ちにする。以前の本文バイトが残る場合も、通常の取得は現在のハッシュに従う。物理パージはこの設計の達成条件にしない。
4. 事実・見解の変化と終了は、新しい記録または終了記録と、**旧記録からその新記録または終了記録への有向リンク**を一回の変更として確定する。リンクには登録時に指定された理由・根拠を結び付けて保持し、読取と検索から辿れるようにする。旧記録は通常の読取・検索に残し、同じ ID の訂正と混ぜない。
5. 誤登録の訂正削除では、記録変更が同じ読取像から**入出両方向の全関係と内部参照リンク**の削除対象を求め、状態台帳が記録と対象を一つの確定単位で論理削除する。関係だけの訂正削除は関係変更が当該関係を論理削除する。削除状態を保持し、通常の読取・検索・連想表示から除く。外部 `Reference` の源ファイルは削除しない。
6. ディレクトリ移動の対応付けは、対象部分木の所属 path を新しい canonical path へ一括で更新し、記録 ID・本文ハッシュ・関係の端点を維持する。失敗時には移動前後の所属が混在しない。移動の通知手段と競合時の扱いは詳細設計で固定する。

本文ハッシュで参照する実体と、読み手が見る現行状態の確定点を分ける。破棄可能な未参照実体が失敗時に残る可能性はあるが、ID、所属、関係、検索対象として露出させない。後続の遅延パージ GC は別の要件・設計で扱う。

## 埋め込みと検索の境界

- 書込みはプロバイダを呼ばずに確定する。確定した本文ハッシュが処理待ちになり、埋め込み処理はそのハッシュの本文を読み、プロバイダ・接続先・モデル・本文ハッシュの組でベクトルを識別して保存する。検索時も選択中の同じ埋め込み環境と現本文ハッシュに一致する成果だけを使う。接続先は base URL の違いを区別できる識別子とし、その具体的な保存表現は詳細設計で定める。訂正後に古いハッシュの処理が完了しても、新しい本文の埋め込みとして採用しない。
- 非同期処理の失敗は記録を巻き戻さない。処理待ち・成功・失敗を区別し、再試行可能な状態を保持する。実行契機と再試行方針は詳細設計で確定する。
- 通常検索は、対象部分木の生存記録に必要な埋め込みが揃い、問い合わせのベクトルが取得できるときに埋め込み方式を使う。使えなければ**対象全体を全文方式で検索**し、方式を結果に示す。一部だけ埋め込み方式で選んで残りを黙って除外しない。
- 明示的な埋め込み検索では利用不能をエラーにし、全文方式に切り替えない。全文方式は本文の語の一致に基づき、意味一致を装わない。全文の索引と順位づけの詳細は詳細設計で決める。
- 候補検索は一致候補と方式を返す。連想表示は候補とは別に `next`、理由、`about`、変化・終了の入出方向を辿り、削除済みの記録・関係を除く。A→B→C の B が候補なら、A と C を前後の手掛かりとして示す。
- 連想表示は候補の一致件数や順位を変えない。記憶ノードから参照される数、関係の種類・方向ごとの接続数、`Reference` の利用状況を統計として扱う。`Reference` の源と範囲を保持し、参照先が解決できない場合は記録を隠さず、その状態を示す。短い要約と統計から重みを計算し、指定予算を超えずに結果を構成する。候補 ID と関係方向を優先し、省略を明示する。予算単位、既定値、計測位置、重みと `Reference` 解決の実装は CLI 契約と詳細設計で固定する。

## CLI と利用者境界

CLI 入出力は、プリミティブ値を引数または `--option=value` で渡す経路と、同じ操作を JSON オブジェクトで渡す経路を持つ。プリミティブな訂正、別 ID の履歴上の変化・終了、誤登録の論理削除は、異なる意図を明示した別操作要求として記録変更へ渡す。本文の差分や時刻から意図を推定しない。混在時の規則、コマンド綴り、引数順、関係識別子、成功・拒否スキーマは別の v7 CLI 契約で定める。ここでは設計や実装から勝手に公開仕様を確定しない。旧 CLI・旧保存形式との後方互換は設けない。ドメイン・埋め込み設定の CRUD を公開しない。

## モジュール単位の検証と統合

| 境界 | 単独で確認する条件 | 統合で確認する条件 |
| --- | --- | --- |
| 記憶モデル／本文保管／状態台帳 | 観測の直接 Reference、信念の任意の理由と型制約、矛盾の信念表現、同 ID 訂正、理由・根拠付き別 ID 変化、入出リンクのカスケード削除、失敗時の不可視性 | CLI から取得・一覧・検索したときの一貫性 |
| ドメイン／状態台帳 | canonical path と部分木移動後の同一 ID・関係 | `--dir` と移動対応付け後の対象範囲 |
| 埋め込み／候補検索 | ハッシュ違いのベクトル非採用、方式選択、明示指定時のエラー | プロバイダなしで書込み、全文フォールバック、後から埋め込み方式 |
| 候補検索／連想表示 | 候補と手掛かりの分離、関係方向、削除の除外、参照数・関係数・`Reference` 利用状況、解決不能状態、予算の上限 | A→B→C、変化・終了、統計を含む出力 |
| CLI／記録変更／関係変更／所属変更／読取操作 | 引数と JSON の同等性、拒否、help・schema・補完・man の一致 | 一時 XDG で v7 の受入例を通す |

各モジュールは契約に対して単独で実装・検証できる。結合検証は実際の保存・検索・CLI を接続して行う。契約や単独テストの成功だけで全体受入を主張しない。

## 実行単位の判断

疎結合の**コード境界**と、実行ファイル・プロセス・Go module の境界は別の決定である。2026-09-29、所有者は以下の B、**CLI 側と埋め込み worker の別プロセス実行**を選んだ。A と C は比較対象として残す。

| 実行配置の候補 | 得られること | 負担と未解決点 |
| --- | --- | --- |
| A. 契約で分けたモジュールを CLI と同じプロセスで接続 | プロセス間通信がなく、ローカル実行を簡潔に保てる | CLI 終了後に埋め込み処理を進める仕組みを別に設計する必要がある。実行単位としての分離はない |
| B. CLI 側モジュールと、確定済み待ち行列を読む埋め込み worker を別プロセスにする | 書込みをプロバイダから切り離し、CLI 終了後も処理を進められる | worker の起動・終了・再試行と状態共有を設計・運用する必要がある |
| C. 記憶庫・検索なども個別プロセス／サービスに分ける | 障害・実行周期をさらに分離できる | プロセス間の契約、配置、可用性、原子的変更の設計と運用が大きく増える |

選択した B では、CLI 側がプロバイダを呼ばずに記録と本文ハッシュ、埋め込み処理待ちを確定する。別プロセスの worker は確定済みの処理待ちと本文ハッシュを読み、対応するベクトルを作る。worker は記録の確定、現本文ハッシュの変更、検索方式の選択を担わない。起動・終了、処理待ちの受渡し、競合、再試行の具体方式は詳細設計で定める。Accepted v7 自体はプロセス配置や Go module 分割を指定していないため、これらは基本設計上の所有者判断として記録する。

## 現行実装からの移し方と計画への入力

現行 [`internal/cli/records.go`](../internal/cli/records.go) は入力検証、保存、埋め込み、候補検索、応答整形を同時に行う。現行 [`internal/search/rank.go`](../internal/search/rank.go) は主に類似度と並び替えを担い、全文検索と連想結果の境界は未実装である。現行 [architecture.md](architecture.md) の埋め込み成功後の確定・キャッシュ欠落時の拒否は、v7 の通常経路に適合しない。

実装計画は、まず共有する値と上記の契約、原子的保存境界を定める。その後、CLI 入出力、埋め込み処理、Reference 解決、全文検索、連想表示など、契約を介して独立に進められる部分を分ける。記録・関係・所属の変更は状態台帳の確定契約に依存するが、相互の実装完了を一律の前提にしない。各モジュールの結合と v7 受入検証には実際の依存と共有資源を反映する。仮の全面直列 `DESIGN_V7 → STORE_V7 → CRUD_V7 → SEARCH_V7 → CLI_V7 → VERIFY_V7 → PROVENANCE_V7` と 27p を正本の計画に適用する前に、この設計を根拠に分解・再見積りする。

## 詳細設計へ渡す未確定事項

Go module の具体的なパス・公開 package・ローカル接続方法、依存方向を確認する方法、worker の起動・終了と処理待ちの受渡し・競合・再試行、永続化のファイル／DB 方式と原子的確定の実装、本文ハッシュの byte 定義、ディレクトリ移動の通知と競合、全文索引と順位、関係の公開 ID、出力予算の単位・既定値・重み・切詰め規則、CLI の正確な綴りと JSON スキーマを詳細設計で決める。これらが未確定でも、複数 Go module の方針、上記の責務分離、v7 の受入義務は緩めない。
