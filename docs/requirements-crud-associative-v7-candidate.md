# agmemx CRUD・CLI・連想検索 要件候補 v7

状態: Candidate（2026-09-28）。v7 は要件文書の候補版であり製品版ではない。v6 の独立レビュー後、所有者が訂正として論理削除した記録を端点とする入出両方向の関係も論理的にカスケード削除する方針を指定したため、新しい版とした。承認前であり、現行の [requirements.md](requirements.md)、設計、実装、PERT を置き換えない。

## 目的と由来

AI エージェントと人が、記憶を登録後にも見つけ、確かめ、訂正し、後から変わった見解や判明事項と結び、不要な記録を除き、関連文脈とともに取り出せるようにする。現行の信念・観測、理由、Reference、`next`、ドメイン、埋め込み検索の制約は、ここで明示する変更を除き [requirements.md](requirements.md) を引き継ぐ。

所有者が指定した変更は、Read に取得・一覧・検索を含む CRUD、対称で一貫した CLI、CLI 引数と JSON 入力を選べること、Git・Docker と同名のコマンドを使うなら主要な意味を揃えること、近接リンクを示す連想検索である。CLI と保存データの後方互換は一切要求せず、破壊的な切替を許す。ドメインは canonical path に対応し、ディレクトリ移動に対応する。プロバイダ不要の書込み、ハッシュ記憶層、非同期の埋め込み、全文検索へのフォールバックも所有者が指定した。誤登録の論理削除と履歴上の終了・変化を区別する。以下の具体化は承認待ちの提案である。

現行の [architecture.md](architecture.md) は埋め込み成功後に記録を確定し、検索時のキャッシュ欠落を拒否する。この候補が承認された場合、その下流設計を改訂する必要がある。現行実装・設計を、この候補のプロバイダ不要書込みやフォールバックの根拠として扱わない。

## CRUD の対象と操作

| 対象 | Create | Read | Update | Delete |
| --- | --- | --- | --- | --- |
| 信念 | 本文と任意の表示名を登録 | ID 指定取得、ドメイン部分木の一覧、自然文検索 | プリミティブな訂正、理由・対象・期間・所属の訂正 | ID 指定の論理削除 |
| 観測 | 本文と Reference、任意の表示名を登録 | ID 指定取得、ドメイン部分木の一覧、自然文検索 | プリミティブな訂正、Reference・期間・所属の訂正 | ID 指定の論理削除 |
| 記録間の関係 | `next` や記憶の変化を表す有向リンクを登録 | 関係の取得・一覧、端点からの参照 | 関係内容の訂正 | 関係の論理削除 |

ドメインそのものと埋め込み設定は CRUD 対象から除く。ドメインはディレクトリの canonical path に対応する文脈・可視範囲であり、記録の所属付け替えと部分木の解決はできる。ディレクトリ移動で canonical path が変わっても記録を新しい path に対応付ける手段を提供し、移動したディレクトリの子孫 path を含む対象記録の ID・本文・理由・`about`・`next`・変化リンクの整合を保つ。移動の検出・通知方法は設計で定める。

作成・取得・一覧・訂正・削除・関係操作・所属変更は埋め込みプロバイダを要求しない。記録本文はハッシュ記憶層に保持し、安定した記録 ID から現在の本文ハッシュへ到達できるようにする。埋め込みは本文ハッシュに紐づく別の再生成可能な情報として非同期に作る。プロバイダ未設定・失敗・処理待ちでも記録の書込みを拒否せず、未作成の埋め込みを作成済みと見せない。ハッシュ方式、格納形態、非同期処理と再試行の仕組みは設計で定める。失敗した記録・関係の変更は、記録 ID、現在の本文ハッシュ、参照、関係、所属索引に部分更新を残さない。

### 訂正と記憶の変化

メモリの更新には二つの異なる意味がある。

1. **プリミティブな訂正**: 登録時の typo や更新ミスを直す。記録 ID を変えず、同じ記録の内容を変更する。関係や参照を壊さず、本文が変われば現在の本文ハッシュを新しい内容に合わせ、対応する埋め込みを非同期処理の対象にする。これは過去の見解の変化を表す操作ではない。
2. **時系列・新事実による変化**: 当時の記録を残し、新しい内容を別記録として登録し、古い記録から新しい記録への有向の変化リンクを作る。変化の理由・根拠をリンクに結び付けられる。リンクを辿ると、何から何へ見解または把握内容が変わったか、登録された理由・根拠は何かが分かる。検索結果でも旧・新の記録と変化の方向、登録された理由・根拠を区別して示す。元の記録を同じ ID で上書きしない。

CLI はこの二つの意図を異なる操作として区別する。本文の差分だけで訂正と見解の変化を推定しない。変化リンクと時系列 `next` は別の意味を持つ。

削除も更新と同じ二種類の意味を区別する。

1. **誤登録・重複などの訂正としての削除**: 同じ ID の記録または誤った関係に削除状態を付ける論理削除とする。記録を論理削除するときは、その記録を端点として参照する関係を、入る向きも出る向きも論理的にカスケード削除する。記録と対象の関係の削除状態は一つの操作として確定し、失敗時に片方だけ削除された状態を残さない。論理削除済み記録は通常の ID 取得・一覧・検索の一致候補にも、連想検索の手掛かりにも本文・要約・ID を出さない。論理削除済み関係も通常の関係取得・一覧・検索と連想手掛かりから隠し、内部の削除状態は保持する。関係を削除せずに、端点の記録だけを訂正として論理削除した状態は作らない。参照中であることだけを理由に記録の論理削除を拒否しない。
2. **後からの事実・見解の変化または終了**: 当時の記録を論理削除せず残し、新しい内容または終了を示す別記録を作り、旧記録から有向の変化・終了リンクを張る。通常検索では旧記録、新記録または終了記録、関係の方向と登録された理由・根拠を出力予算の範囲で示す。過去にそう考えた事実を、誤登録として隠さない。

この二つは CLI の異なる操作で選び、本文や時刻だけから自動判定しない。物理パージは遅延するルーズな GC として後続で実装するが、この候補の CRUD 受入には含めない。GC の時期、到達可能な履歴の保護、復元可否は後続要件・設計で定める。論理削除だけで物理パージ済みと表示しない。

## CLI 入出力

公開コマンドは対象ごとに同じ操作語と引数順を用い、対応する操作の有無を `help`、`schema`、補完、man に一致させる。同名操作の主要な意味を対象によって変えない。Git・Docker と同じ名前を使う場合は利用者が期待する主な意味と揃え、揃わない名前は採用しない。具体的なコマンド綴り、関係の識別方法、JSON フィールドは設計・CLI 契約で定める。

本文、表示名、ID、期間の両端、Reference の源と範囲、理由の種別と ID、関係の種別・両端・理由、ドメイン、検索語、出力予算など、プリミティブ値で表せる入力はコマンド引数または `--option=value` 形式で指定できる。複数値も意味を曖昧にせず表せる範囲では反復オプションや分割オプションを提供する。同じ公開操作には JSON オブジェクト入力も用意し、呼び出し側が CLI 引数経路または JSON 経路を選べる。JSON を通常操作の必須入力にはしない。同一呼び出しで両経路を混在させる場合は一つの明確な優先・拒否規則を持つ。

人向け text と機械向け JSON で、取得・一覧・検索の記録 ID、内容、関係を確認できる。成功形と拒否は厳密なスキーマを持つ。互換エイリアス、旧コマンド・旧応答形、旧保存形式の読取・変換・保全は要求しない。旧データに関する追加の移行手順を要件化しない。

## 出力予算内の連想検索

自然文検索は、指定ドメイン部分木で埋め込み検索が利用可能ならそれで一致候補を選ぶ。プロバイダや必要な埋め込みが利用できない通常検索では、対象記録を黙って除外せず全文検索へフォールバックする。呼び出し側が埋め込み検索を明示指定した場合は全文検索へ切り替えず、利用不能をエラーとして返す。検索結果には実際に使った検索方式を示す。全文検索でも検索語が重ならない記録を意味一致したと偽らない。検索方式の判定と全文検索の索引・順位づけは設計で定める。

一致候補には直接の `next` 前後、理由、`about`、変化・終了リンクから辿れる記録を連想の手掛かりとして加える。訂正として論理削除された記録は一致候補・手掛かりに加えず、論理削除された関係は手掛かり生成に使わない。記録の論理削除によりカスケード削除された関係も、連想検索では表示・辿り直しをしない。手掛かりは自身の検索スコアが低くても除外しない。A→B→C の B が一致したときは A が前、C が後と分かり、B の変化前後や終了を示す記録と理由も `next` とは異なる関係として分かる。候補本体と手掛かりを区別し、手掛かりを一致件数・順位に混ぜない。

各候補には、参照されている数、関係の種別・方向ごとの接続数、Reference の利用状況などの統計を付ける。表示する短い要約は保存本文、表示名、Reference の解決可能な文脈に基づき、由来のない意味を事実として追加しない。Reference の源と範囲は保持し、参照先を解決できない場合は記録を消さず、その状態を示す。

検索表示は指定された出力予算を守る。重み付けで、候補の関連度に加え、参照・接続の統計、リンクの種類と方向、時系列の前後、見解の変化を考慮し、予算内に入る候補・手掛かり・要約の量を選ぶ。限られた予算でも候補 ID と関係方向を優先し、省略があれば件数または省略の事実を示す。予算の単位と既定値、統計の厳密な定義、重み・選択・切詰め規則は設計・CLI 契約で決める。同一入力での結果の再現性は受入条件としない。ID から元の記録と関係全体へ進める。

## 受入の最低例

1. 一時 XDG 領域で信念・観測・関係を通常の引数だけで作成し、各対象を取得・一覧で読み戻せる。同じ操作を JSON 入力経路でも実行できる。ドメインと埋め込み設定の CRUD は公開しない。
2. プロバイダ未設定でも記録を作成・訂正でき、ID と本文ハッシュの対応が読み戻せる。typo 訂正後は同じ ID から訂正済み本文が得られ、無関係の記録・参照・関係は変わらない。不正な参照などで記録変更が失敗したときは、記録・索引に部分更新を残さない。後から非同期処理で作られた埋め込みが、対応する本文ハッシュに結び付く。
3. 古い見解と新しい見解または終了を示す内容を別 ID の記録として保持し、理由・根拠を含む有向の変化・終了リンクから両方を辿れる。検索で片方が一致すると、出力予算の範囲で相手の ID、変化・終了の方向、理由・根拠の存在が分かる。元記録の本文は変わらず、通常検索からも隠れない。
4. A→B→C を登録し、B にだけ一致する語で検索すると、B を一致候補として、A と C の前後関係を手掛かりに表示する。理由・`about`・変化リンクを時系列関係と区別し、予算を縮めた場合も省略を明示する。参照数などの統計と重みを使い、出力予算を超えない。結果の同一性は判定対象にしない。
5. 埋め込みが利用できない通常検索は全文検索の結果と検索方式を返す。明示的な埋め込み検索は利用不能エラーを返し、全文検索の結果にすり替えない。埋め込み作成後は本文ハッシュに対応するベクトルを検索に利用できる。
6. 誤登録の記録は関係から参照中でも同じ ID を論理削除でき、入出両方向の関係も同じ操作で論理削除される。失敗時は記録も対象の関係も削除状態を変えない。削除済み記録は通常の ID 取得・一覧・検索の一致候補・連想手掛かりに現れない。カスケード削除された関係と個別に論理削除された誤った関係は、通常の関係取得・一覧・検索と連想手掛かりに現れず、内部の削除状態は残る。事実の変化や終了はこの削除操作を使わず、旧記録と新記録または終了記録のリンクとして検索に現れる。論理削除を物理パージ済みとは表示しない。全公開操作の help・schema・text・JSON・補完・man が同じ体系を示す。
7. ディレクトリの canonical path が移動した後、提供された対応付け手段により、新 path から対象記録の同じ ID・本文・関係を取得・一覧・検索できる。無関係のドメインは変わらない。

## 次の設計で決めること

関係の識別子と訂正方法、終了を示す記録の型とリンク表現、ディレクトリ移動の検出または通知手段、ハッシュ記憶層と埋め込みの非同期処理、全文検索の実装、検索統計の計算法、出力予算の単位・既定値・重み・要約方式、CLI の正確な綴りと JSON スキーマを設計で具体化する。これらの選択は、訂正と記憶の変化・終了の区別、プロバイダ不要の書込み、明示指定時の埋め込み検索エラー、誤登録の論理削除、関係方向、予算内表示、後方互換不要という要件を変更できない。遅延パージ GC は後続の実装対象として計画するが、この候補の CRUD 受入条件ではない。
